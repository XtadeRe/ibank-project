# Docker Agent (Docker Stack Orchestrator) — описание

## Что это за проект
**Docker Agent** — это небольшое backend-приложение на **Node.js (Express)**, которое управляет Docker-стеками через **docker-compose**. Проект предоставляет REST API, позволяющее:
- получить список запущенных/существующих стеков на хосте,
- получить информацию по контейнерам стека и назначенным портам,
- запустить новый стек: 
  - клонирует репозиторий (по переданной ветке),
  - записывает `.env` для compose,
  - запускает нужный compose-файл,
  - выполняет доп. шаги инициализации для некоторых типов стеков (миграции Laravel и т.п.),
- удалить стек (остановка и удаление контейнеров + удаление папки стека),
- перезапустить стек (docker-compose restart) и перезапустить контейнер.

Стек в этой архитектуре — это группа контейнеров, имена которых формируются с использованием префикса `stackName` (например: `${stackName}_app`, `${stackName}_php`, `${stackName}_web` и т.д.).

## Архитектура (как устроено)
- **server.js**
  - Поднимает Express на порту `3001`.
  - Задаёт `global.STACKS_DIR` — базовую папку, куда будут клонироваться/храниться стеки.
  - Хранит `global.activeOperations` (Map) для отслеживания прогресса асинхронных операций.
- **routes/** (эндпоинты API)
  - `routes/index.js` собирает все роуты в единый `/api`.
  - `routes/health.js` — проверка доступности сервиса.
  - `routes/stacks.js` — работа со стеками.
  - `routes/operations.js` — получение статуса операции.
  - `routes/branch-data.js` — получение списка веток из GitHub.
- **controllers/**
  - `StackController.js` — контроллеры операций над стеком.
  - `OperationController.js` — чтение статуса операции из `global.activeOperations`.
  - `BranchController.js` — получение веток GitHub.
- **utils/dockerUtils.js**
  - Реализует основную «оркестрацию»:
    - инвентаризация контейнеров/стеков,
    - вычисление портов,
    - старт/удаление стека,
    - ожидание готовности ключевых контейнеров,
    - кеширование результатов.

## REST API (основные эндпоинты)
Базовый путь: **`/api`**

### 1) Health
- `GET /api/health`
  - Возвращает `{ status: 'ok' }`.

### 2) Ветки GitHub
- `GET /api/branch-data`
  - Вызывает GitHub API: список веток репозитория `XtadeRe/ibank-project`.
  - При ошибке возвращает запасной список: `['main','master','develop','createStack']`.

### 3) Стеки
Все эндпоинты ниже относятся к `routes/stacks.js`:

- `GET /api/stacks`
  - Возвращает список стеков, найденных по именам контейнеров на Docker-хосте.

- `GET /api/stacks/:name/info`
  - Возвращает детальную информацию по контейнерам стека + порты + формирует локальные URL (app/web/frontend/phpmyadmin) на базе найденных портов.

- `GET /api/stacks/:name/ports`
  - Возвращает только порты стека и соответствующие URL.

- `POST /api/stacks/:name/up`
  - Запуск стека.
  - Body:
    - `git_branch` — ветка репозитория,
    - `stackType` — тип compose-набора.
  - Возвращает сразу `operationId`, запуск выполняется асинхронно в фоне.

- `POST /api/stacks/:name/delete`
  - Удаление стека (в фоне), также возвращает `operationId`.

- `POST /api/stacks/:name/restart`
  - Перезапуск стека через `docker-compose ... restart`.
  - Compose-файл выбирается по `.env` в папке стека и маппингу.

- `POST /api/stacks/containers/:id/restart`
  - Перезапуск отдельного контейнера: `docker restart <containerId>`.

### 4) Статус операций
- `GET /api/operations/:operationId/status`
  - Возвращает статус/прогресс/сообщение и (если есть) результат операции из `global.activeOperations`.

## Логика запуска стека (что делает `startStackAsync`)
1. Пауза фонового обновления кешей (чтобы меньше мешать инвентаризации).
2. Создание `operationId` и запись операции в `global.activeOperations`.
3. Подготовка директории стека:
   - если папка `STACKS_DIR/<stackName>` существует — удаляется.
4. Клонирование репозитория:
   - `git clone --branch <git_branch> --depth 1 https://github.com/XtadeRe/ibank-project.git <stackDir>`
5. Выбор compose-файла по `stackType`.
6. Генерация `.env` в корне папки стека (значения портов и параметров окружения).
7. Запуск docker-compose:
   - `docker-compose --env-file .env -f <composeFile> -p <stackName> up -d`
8. Ожидание ключевых контейнеров (например, `${stackName}_app`, `${stackName}_php`).
9. Доп. шаги:
   - для `full` выполняются команды внутри PHP контейнера:
     - `php artisan key:generate --force`
     - `php artisan migrate --force`
     - `php artisan config:clear`
   - для `stack` дополнительно выполняется подстановка порта в `.html` файлы внутри `frontend`.
10. Формирование результата: финальные порты и URL, установка операции как `completed`.

## Логика удаления стека (что делает `deleteStackAsync`)
1. Остановка контейнеров стека: `docker rm -f` по контейнерам с именами, содержащими `stackName`.
2. Очистка кешей.
3. Удаление папки стека: `rm -rf <STACKS_DIR>/<stackName>` (на уровне Node.js `fs.rmSync`).
4. Установка операции как `completed/failed`.

## Требования к окружению (Windows)
Для корректной работы на Windows хосте необходимо:
1. **Docker Desktop** + запущенный Docker Engine.
2. Должны быть доступны команды:
   - `docker`
   - `docker-compose` (или совместимый wrapper, но в коде используется `docker-compose`, а не `docker compose`).
3. **Git** (чтобы `git clone` работал из процесса Node.js).
4. Доступ в интернет к GitHub репозиторию `XtadeRe/ibank-project`.
5. Запускаемый Node.js сервис должен иметь:
   - права на выполнение Docker команд,
   - права на запись/удаление папок в `STACKS_DIR`.

## Что нужно изменить при переносе на другую машину (Windows → Windows)
Самое важное — корректно настроить путь `STACKS_DIR` и окружение команд.

### 1) Путь хранения стека (`global.STACKS_DIR`)
В `server.js` сейчас задан фиксированный Windows-путь:
- `C:/OSPanel/home/docker-agent/docker-stacks/yml`

На другой машине этот путь, скорее всего, будет другим. Нужно:
- изменить строку в `server.js` на актуальную папку, например:
  - `D:/docker/docker-stacks/yml`
  - или `C:/docker-agent/docker-stacks/yml` (как вам удобнее).

Именно в эту папку будут клонироваться репозитории стека и появляться `.env`/файлы compose.

### 2) Убедиться, что в PATH доступны `docker`, `docker-compose`, `git`
Если на новой машине команды вызываются из терминала, но из Node.js не находятся — значит проблема в окружении/переменных.
- Обычно помогает установка Docker Desktop / Git и перезапуск сервиса.

### 3) Нужные сетевые/портовые ограничения
Проект сам генерирует порты динамически (через случайные смещения вокруг базовых). Однако:
- на новой машине должны быть свободны диапазоны портов,
- корпоративные firewall/политики могут блокировать входящие соединения.

### 4) Сопоставление compose-файлов и типов стека
В коде есть маппинг `stackType -> compose файл`:
- `full`  -> `docker-compose.ib.yml`
- `stack` -> `docker-compose.compass.yml`
- `backend` -> `docker-compose.compass.java.yml`
- `db` -> `docker-compose.compass.db.yml`

Если в репозитории или в compose-файлах на целевой машине структура/имена отличаются — нужно синхронизировать compose-файлы или обновить маппинг.

### 5) Перезапуск стека использует выбор compose-файла по наличию файлов
При `restartStack` код ищет подходящий compose-файл в папке стека, опираясь на список из маппинга + `docker-compose.yml/docker-compose.yaml`.
Если на новой машине структура папки стека отличается — перезапуск может не найти корректный compose-файл.

### 6) Secrets/пароли БД
В генерируемом `.env` значения `DB_PASSWORD` и `DB_ROOT_PASSWORD` заданы пустыми строками.
- Если у вас настроены реальные пароли — нужно менять генерацию `.env` в `utils/dockerUtils.js` (или вынести конфигурацию в env/конфиг).

## Как запустить (кратко)
1. Установите зависимости:
   - `npm ci` или `npm install`
2. Запустите сервер:
   - `npm start`
3. Проверьте:
   - `GET http://localhost:3001/api/health`

## Примечания по использованию
- Запуск/удаление стека выполняется асинхронно, поэтому нужно отслеживать `operationId` через `GET /api/operations/:operationId/status`.
- Сервис периодически обновляет кеши (раз в минуту) и при старте/удалении делает паузу, чтобы снизить влияние на фоновые расчёты.
